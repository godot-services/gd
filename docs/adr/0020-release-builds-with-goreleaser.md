# 0020. Release builds with GoReleaser

- Status: accepted
- Date: 2026-10-21
- Refs: gd#41

## Context

Users need prebuilt `gd` binaries for linux, macOS and windows on amd64 and
arm64, so they do not need a Go toolchain. Releases v0.1.0–v0.3.0 were created
by hand together with their tag (`gh release create vX --notes ...`) and have
hand-written notes. gd#42 will publish to package managers that consume the
release archives.

## Decision

- GoReleaser v2 (pinned version) builds, archives and uploads, configured in
  `.goreleaser.yaml` and run by `.github/workflows/release.yml` on `v*` tags.
- Six targets, `CGO_ENABLED=0`, `-trimpath`. Archives
  `gd_<version>_<os>_<arch>.tar.gz` (`.zip` on windows) with `gd`, `README.md`
  and `LICENSE`, plus `checksums.txt` (SHA-256).
- Release flow: push only the tag (`git tag vX && git push origin vX`); the
  workflow creates the release with the assets and a changelog generated by
  GitHub; afterwards `gh release edit vX --title "vX: ..." --notes-file ...`
  sets the title and notes. Creating the release first with `gh release create`
  is not used: GoReleaser v2 then overwrites its title with the tag, makes it a
  draft during the upload and resets a prerelease flag; only the notes survive.
- `release.mode: keep-existing` and `replace_existing_artifacts`: a re-run after
  a failed or partial upload keeps the edited notes and replaces the assets (the
  title falls back to the tag and has to be edited again).
- The PR workflow runs `goreleaser release --snapshot --clean`, so a broken
  config or a target that does not compile fails the PR, not the tag.

Rejected: a hand-written `go build` matrix. It needs no tool, but more YAML and
shell, and gd#42 would have to generate formulas and manifests itself, which
GoReleaser does from the same config.

## Consequences

A release is one tag push. The pipeline depends on GoReleaser and its action;
the version is pinned and raised on purpose. The upload part only runs on a real
tag, so it is first exercised by the next release.
